# 분산 캐시(Redis) 아키텍처와 운영

> 대규모 트래픽에서 캐시 구조가 어떻게 진화하고, 운영 중 무엇을 신경 써야 하는지 정리

## 1. 캐시 구조의 진화 방향

```
user server + remote cache
  → gateway + user server
  → gateway + passport(인증 분리)
  → gateway + local cache + sticky session
  → gateway + cassandra
```

처음에는 각 서버가 원격 Redis를 직접 조회해 네트워크 왕복(RTT)이 병목이 된다. gateway 계층을 두어 인증/라우팅을 분리한 뒤, **local cache + sticky session**(같은 유저 요청을 같은 인스턴스로 고정)을 도입하면 remote RTT 자체를 없앨 수 있다. 캐시로도 감당 안 되는 콜드 데이터·대용량 조회는 Cassandra 같은 분산 DB로 역할을 분리한다.

흐름을 한 줄로 요약하면: *원격 캐시 의존 → 로컬 캐시로 레이턴시 제거 → 감당 안 되는 영역은 전용 스토리지로 분리*.

## 2. Remote-Local 정합성: 무효화 전파

로컬 캐시를 쓰면 원격 데이터가 바뀌어도 로컬은 즉시 알 수 없다(stale). 먼저 "데이터가 얼마나 오래돼도 되는지" stale 허용 범위를 정의한 뒤, 변경을 전파할 채널을 고른다.

- **pub/sub**: 변경 시 무효화 이벤트를 broadcast. 구독이 끊기면 메시지가 유실됨(at-most-once)
- **stream**: 컨슈머 그룹 기반으로 offset을 유지해, 재연결 후에도 놓친 이벤트를 다시 읽을 수 있어 pub/sub보다 신뢰성이 높음

## 3. 메모리와 조회 효율화

- **자료구조 선택**: 플래그성 데이터(출석, 읽음 여부)는 **bitmap**으로 저장해 메모리를 크게 절약
- **hotkey 처리**: 특정 key에 요청이 쏠리면 해당 노드에 부하가 집중되므로, 로컬 캐시에 hotkey를 별도로 두거나 키를 샤딩해 분산
- **Binary 포맷**: JSON 대신 Protobuf/MessagePack 등 바이너리 직렬화로 저장 공간과 역직렬화 비용을 줄임
- **해시 태그로 SLOT 분배**: Redis Cluster는 key를 해시해 16384개 슬롯에 분산하는데, `{}`로 묶은 해시 태그를 쓰면 여러 key를 같은 슬롯(= 같은 노드)에 묶어 multi-key 연산이 가능해짐
- **MGET 최적화**: 같은 슬롯끼리 묶어서 MGET을 날려야 Cluster 환경에서 cross-slot 에러 없이 효율적으로 조회됨

## 4. 원자적 처리와 버전 관리

- **Lua script (EVAL)**: "조회 후 조건부 갱신"처럼 여러 명령을 하나의 원자적 연산으로 묶을 때 사용 — Redis가 싱글 스레드로 실행하므로 중간에 다른 명령이 끼어들지 못함
- **Dual write 후 read 버전업**: 캐시 스키마를 바꿀 때 구/신 버전에 동시에 write하다가, 신버전 데이터가 충분히 쌓이면 read 트래픽을 신버전으로 전환 — 무중단으로 캐시 구조를 롤아웃하는 전략

## 5. 순간 요청량 대응: write-behind

쓰기 요청을 DB에 바로 쓰지 않고 **Redis를 1차 SSOT**로 즉시 반영한 뒤, 비동기 컨슈머가 배치로 모아 DB에 적재한다. 순간 트래픽 스파이크에도 DB 커넥션/쓰기 부하를 흡수할 수 있다.

## 6. 운영 장애 포인트

운영 사고는 대부분 **블로킹 커맨드**에서 발생한다.

| 상황 | 대응 |
|------|------|
| 캐시 적중률 하락 | TTL, 키 설계, hotkey 여부 점검 |
| 큰 자료구조 삭제 | `DEL`(동기, 블로킹) 대신 `UNLINK`(비동기 메모리 반환) |
| 전체 키 조회 | `KEYS`(O(N) 블로킹) 대신 커서 기반 `SCAN` |
| 키 구조 변경 | 실제 key와 버전/별칭을 분리하는 indirection key 설계 |
| 클러스터 리샤딩 | 클라이언트가 최신 토폴로지를 다시 읽도록 topology refresh |
| 느린 명령 | `SLOWLOG`로 느린 명령(대용량 KEYS, SORT) 식별·제거 |

## 핵심 정리

- 캐시 아키텍처는 "원격 캐시 → 로컬 캐시 + sticky routing → 전용 스토리지 분리" 방향으로 진화한다
- 로컬 캐시를 쓰는 순간 정합성 문제가 생기므로, pub/sub보다 **신뢰성 있는 무효화 채널(Stream)** 설계가 중요하다
- 대량/원자적 연산은 Redis Cluster의 슬롯 구조(해시 태그)와 Lua script를 이해해야 올바르게 설계할 수 있다

# 분산락 구현 원리
> 공통 서비스로 분산락 제공할 때 필요. [[대규모 트래픽 DB 설계와 정합성]]의 "분산락은 어떻게 구현할까?" 심화

## 분산 락이 필요한 이유 (동시성 문제)

단일 프로세스 내 락(synchronized, ReentrantLock)은 같은 JVM 안에서만 유효하다. 서버가 여러 대로 수평 확장되면, 서로 다른 프로세스가 동시에 같은 자원(재고 차감, 포인트 적립, 중복 결제 방지 등)에 접근할 수 있어 **프로세스 경계를 넘는 락**이 필요하다. 분산락은 이 역할을 외부 공유 저장소(ZooKeeper, Redis, DB)에 위임한다.

## ZooKeeper 기반 분산 락 (Ephemeral + Sequential Node)

- 락을 획득하려는 클라이언트가 `/lock/lock-` 경로 아래에 **Ephemeral + Sequential** 노드를 생성 (예: `lock-000001`)
- 자신보다 순번이 낮은 노드가 없으면 락 획득, 있으면 바로 앞 순번 노드에 **watch**를 걸고 대기
- 앞 노드가 삭제되면(락 해제 또는 세션 종료) watch 콜백으로 깨어나 재확인 — thundering herd 없이 순차적으로 락이 넘어감
- Ephemeral 노드이므로 클라이언트가 죽거나 세션이 끊기면 ZooKeeper가 자동으로 노드를 삭제 → 락이 자동 해제됨 (TTL 설정이 필요 없다는 게 Redis 방식과의 큰 차이)

## Redis 기반 분산 락 (SETNX, Redlock 알고리즘)

- 가장 단순한 형태: `SET key value NX PX 30000` — "키가 없을 때만 생성 + TTL 설정"을 원자적으로 수행
- 단일 Redis 인스턴스에만 의존하면 그 인스턴스가 장애 나는 순간 락 시스템 전체가 멈추거나, failover 중 복제 지연으로 **같은 락을 두 클라이언트가 동시에 획득**하는 문제가 생길 수 있음
- **Redlock**: 서로 독립적인 N개(보통 5개)의 Redis 노드에 각각 락 획득을 시도하고, **과반수(N/2+1) 이상에서 성공 + 전체 소요 시간이 TTL보다 충분히 짧을 때만** 유효한 락으로 인정

## Redlock의 한계와 Martin Kleppmann의 비판

Kleppmann은 Redlock이 "성능을 위한 락(효율성)"에는 충분하지만, "정확성을 위한 락(안전성 보장)"으로 쓰기엔 위험하다고 지적했다.

- **GC pause / 프로세스 지연**: 락을 획득한 클라이언트가 긴 GC pause에 빠지면, 그 사이 TTL이 만료되고 다른 클라이언트가 같은 락을 획득 → pause가 끝난 첫 클라이언트는 자신이 여전히 락을 들고 있다고 착각한 채 작업을 이어감(두 클라이언트가 동시에 임계구역 진입)
- **클럭 점프**: NTP로 시간이 갑자기 보정되거나 관리자가 시스템 시간을 수동으로 바꾸면 TTL 계산이 깨짐
- 결론: Redlock은 **fencing token 없이는 안전성(safety)을 완전히 보장하지 못한다**는 것이 핵심 비판

## 분산 락 vs 낙관적 락 vs DB 락 비교

| 구분 | 분산 락 (ZK/Redis) | 낙관적 락 (버전 컬럼) | DB 락 (SELECT FOR UPDATE) |
|------|---------------------|------------------------|----------------------------|
| 충돌 처리 시점 | 진입 전에 차단 | 커밋 시점에 감지 | 진입 전에 차단 |
| 적합한 상황 | 서비스 간 공유 자원, 분산 환경 전반 | 충돌이 드문 경우 | 단일 DB 내 로우 단위 동시성 제어 |
| 확장성 | 외부 저장소에 의존, 수평 확장 용이 | 재시도 로직 필요 | DB 커넥션/트랜잭션에 종속적 |
| 장애 시 위험 | TTL 관리 실패 시 중복 획득 가능 | 재시도 폭주 가능 | 긴 트랜잭션이 다른 요청을 블로킹 |

## Fencing Token 패턴

Redlock의 한계를 보완하는 핵심 장치.

1. 락을 획득할 때마다 **단조 증가하는 토큰 번호**(fencing token)를 함께 발급
2. 클라이언트는 공유 자원에 접근할 때 이 토큰을 같이 전달
3. 자원을 보호하는 쪽(예: 스토리지 서버)은 **자신이 마지막으로 본 토큰보다 작은 토큰의 요청을 거부**

이렇게 하면 GC pause 등으로 TTL이 만료돼 다른 클라이언트가 새 토큰으로 락을 획득한 이후, 뒤늦게 깨어난 이전 클라이언트가 (더 작은) 옛 토큰으로 요청을 보내도 자원 쪽에서 거부할 수 있다 — 락 자체의 정확성이 아니라 **자원 접근 시점의 순서를 보장**함으로써 문제를 해결하는 접근.

## 핵심 정리

- ZooKeeper 방식은 세션 기반 자동 해제로 안전하지만 인프라가 무겁고, Redis 방식은 가볍지만 TTL 관리 책임이 클라이언트에 있다
- Redlock은 과반수 합의로 단일 노드 장애에는 강하지만, **GC pause·클럭 문제로 인한 안전성 결함**은 근본적으로 해결하지 못한다
- 진짜 정확성이 필요한 자원 보호에는 분산락만으로 끝내지 말고 **Fencing Token**을 함께 적용해야 한다

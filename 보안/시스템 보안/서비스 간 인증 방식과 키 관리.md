# 서비스 간 인증 방식과 키 관리

> 내부/외부 서비스 간 호출을 무엇으로 인증하고, 키를 어떻게 안전하게 교체할지 정리

## 1. 인증 방식 선택: 무엇을 신뢰 단위로 삼는가

| 방식 | 핵심 원리 | 주로 쓰는 상황 |
|------|-----------|----------------|
| **API Key** | 고정된 키를 요청에 실어 보냄 | 구현이 단순한 외부 파트너 연동 |
| **OAuth2** | 토큰 발급 서버에서 access token 발급, scope로 권한 제어 | 제3자 위임 인증, 사용자 대신 접근 |
| **mTLS** | 클라이언트·서버가 서로의 인증서를 검증(양방향 TLS) | 서비스 간(east-west) 트래픽, 네트워크 레벨 신뢰 |
| **JWT** | 서명된 토큰 안에 클레임을 담아 자체 검증 가능 | 세션리스 인증, 마이크로서비스 간 권한 전파 |
| **HMAC signature** | 공유 비밀키로 요청 본문을 서명해 변조 여부 검증 | 웹훅/외부 API처럼 메시지 무결성이 중요한 경우 |

API Key/HMAC은 메시지 단위 신뢰, mTLS는 연결 단위 신뢰, OAuth2/JWT는 권한(scope/claim) 단위 신뢰로 범위가 다르다. 실무에서는 mTLS로 연결 신뢰를 세우고 그 위에 JWT로 권한을 전파하는 식으로 조합해서 쓰는 경우가 많다.

## 2. 키 교체: 무중단 rotation

- **key rotation library**: 애플리케이션 코드 변경 없이 키를 주기적으로 교체 — 키 ID(kid)를 헤더/메타데이터에 함께 보내 어떤 버전의 키로 서명했는지 구분
- **migration 기간**: 옛 키로 서명된 데이터가 남아 있는 동안은 **신·구 키를 동시에 검증 가능한 상태**(dual key 기간)를 유지해야 무중단 전환이 가능하다

## 3. 외부사 연동: 노출 최소화

- **유저 키(Hash, UUID)**: 외부 파트너사에 내부 식별자를 그대로 노출하지 않고 해시값·UUID로 가공한 식별자를 발급
- **caller 식별과 내부/외부 통신 차이**: 호출 주체가 내부 서비스인지 외부 파트너인지에 따라 인증 수준·로깅 정책을 다르게 적용(내부는 가벼운 인증, 외부는 강한 인증 + rate limit)
- **TCP gateway**: 외부사와의 연동을 애플리케이션이 직접 맺지 않고 전용 게이트웨이에서 TCP 레벨 연결(풀링, 장애 격리)을 관리

## 4. 서비스 간 호출 통제

- **Service mesh + mTLS**: 사이드카 간 통신을 자동으로 mTLS로 암호화하고 인증서 발급/갱신을 메시가 중앙에서 관리
- **api path policy / whitelist**: 특정 경로를 호출할 수 있는 서비스를 정책으로 제한하고, 허용된 호출자 목록만 접근 가능하도록 해 내부 API의 임의 호출도 차단

## 핵심 정리

- 인증 방식은 "무엇을 신뢰 단위로 삼는가"(요청/연결/권한)에 따라 고르며, 정답은 하나가 아니라 상황별 조합이 일반적이다
- 키 교체는 교체 자체보다 **신·구 키를 동시에 지원하는 기간 설계**가 핵심이다
- 외부 연동은 내부 식별자를 그대로 노출하지 않는 것이 기본 원칙이고, 내부 통신도 whitelist·path policy로 암묵적 신뢰를 최소화해야 한다

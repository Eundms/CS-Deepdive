# 로그·메트릭 파이프라인 설계

> 대용량 로그를 안정적이면서 저비용으로 수집·적재하는 구조 정리

## 1. 로그 구성: 무엇을, 어떻게 남길까

- **전송 경로**: 특정 레벨(ERROR 등) 이상은 알림 appender로 바로 Slack 등에 전파하고, 대량 로그는 kafka appender로 보내 중앙 집계 파이프라인(ELK 등)으로 흘려보냄
- **정형 vs 비정형**: JSON처럼 구조화된 로그는 파싱·검색이 쉽지만 용량이 크고, 비정형(평문) 로그는 가볍지만 분석 시 추가 파싱이 필요함
- **민감정보/용량 관리**: req/res, param을 로깅하되 민감정보(주민번호, 계좌번호)는 masking하고, 과도하게 큰 payload는 size 제한을 둬 로그 용량 폭증을 막음

## 2. 로그 파이프라인의 가용성 우선순위

로그 파이프라인이 막히는 상황에서는 **서비스 가용성 > 로그 완전성**이 원칙이다.

- **전송 실패 시**: 즉시 재시도하고, 그마저 실패하면 로컬 파일로 fallback(retry + file)해 유실을 방지
- **버퍼 포화 시**: Logback AsyncAppender는 버퍼가 가득 차면 기본적으로 블로킹되는데, `neverBlock=true`로 두면 로그가 드랍되더라도 애플리케이션 스레드는 멈추지 않는다. 대신 드랍율·버퍼 사용률을 메트릭화해 **문제를 빨리 발견**할 수 있어야 한다

## 3. Kafka 적재 시 부하 분산

같은 key로만 계속 보내면 특정 파티션에 쏠리므로, producer batching에 **key rolling**(일정 주기로 key를 돌려가며 배치 전송)을 적용해 여러 파티션에 고르게 분산한다.

## 4. 로그 비용 절감

- **수집기 경량화**: Logstash 대신 Rust 기반의 가벼운 **Vector**를 도입해 리소스 사용량과 처리 지연을 줄임
- **저장 엔진 교체**: Elasticsearch보다 저장 비용이 낮은 **VictoriaLogs**로 적재하고, 기존 Kibana UI는 adapter를 통해 그대로 사용해 운영 경험은 유지하면서 비용을 절감

## 핵심 정리

- 로그 설계의 핵심은 "얼마나 구조화할지"와 "민감정보를 어떻게 다룰지(masking)"의 균형이다
- 로그 파이프라인이 막히는 상황에서는 서비스 가용성이 우선이며, neverBlock·retry+file 같은 fallback이 이를 뒷받침한다
- 로그 비용은 결국 저장 엔진 선택(ELK → VictoriaLogs)과 수집기 경량화(Logstash → Vector)로 줄인다

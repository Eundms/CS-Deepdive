# 테스트·마이그레이션·배치·워크플로우 전략

> 테스트 환경 정합성, 안전한 마이그레이션, 배치/워크플로우 오케스트레이션을 어떻게 다룰지 정리

## 1. 테스트 환경의 정합성

- **H2 vs MySQL**: 인메모리 H2는 빠르지만 실제 운영 DB와 SQL 방언·제약조건 동작이 미묘하게 달라 운영에서만 터지는 버그가 생길 수 있음
- **Testcontainer**: 테스트 실행 시 실제 MySQL(운영과 동일한 엔진)을 Docker 컨테이너로 띄워 테스트 — 속도는 H2보다 느리지만 운영 환경과의 괴리를 없애 신뢰도를 높인다

## 2. 아키텍처 규약의 자동화

- **ArchUnit**: 패키지 의존 방향, 레이어 간 호출 규칙(예: controller가 repository를 직접 호출 금지) 같은 규약을 테스트 코드로 강제
- **Konsist**: Kotlin 생태계에서 코드 컨벤션·아키텍처 규칙을 선언적으로 검증

리뷰에서 매번 지적하는 대신 빌드 단계에서 자동으로 걸러내는 것이 목적이다.

## 3. 마이그레이션 안전성 확보

- **shadow(섀도 운영)**: 신규 시스템/로직을 실제 트래픽과 함께 돌리되 결과는 실사용에 반영하지 않고 비교만 함
- **dry-run**: 실제 쓰기 없이 로직만 실행해 "진짜 실행하면 어떤 변화가 생기는지" 미리 확인

두 방법 모두 목적은 같다 — **전환하기 전에, 전환해도 안전하다는 확신을 데이터로 얻는 것**이다.

## 4. 글로벌 대응의 범위

다국어 적용은 UI 문자열뿐 아니라 **코드(enum/상수)에 박힌 텍스트와 admin DB에 저장된 데이터**까지 대상에 포함해야 한다. 하드코딩된 한국어 문자열이 코드/DB 곳곳에 퍼져 있어 전수 조사가 필요한 작업이다.

## 5. 반복 작업의 오케스트레이션 전환

복잡도가 커질수록 상태 관리가 내장된 도구로 옮겨가는 패턴이 반복된다.

- **배치**: 단순 반복이면 K8s CronJob으로 충분하지만, 배치 간 의존성(DAG)·재시도·실패 알림·백필이 필요해지면 **Airflow**로 전환
- **Workflow**: 결제 → 정산 → 알림처럼 여러 단계로 이어지는 프로세스를 Kafka 이벤트 체인으로 구현하면 상태 추적과 보상 트랜잭션(실패 시 롤백)이 복잡해지는데, **Temporal**은 durable execution(실행 상태 자체를 지속적으로 저장)으로 재시도·타임아웃을 코드 레벨에서 선언적으로 다룰 수 있게 해준다

## 핵심 정리

- 테스트는 "빠른 피드백(H2)"과 "운영과 동일한 신뢰도(Testcontainer)"의 트레이드오프이며, 아키텍처 규약은 ArchUnit/Konsist로 자동화해 리뷰 비용을 줄인다
- 마이그레이션 안전성은 결국 **shadow + dry-run으로 "실행 전에 결과를 미리 본다"**는 원칙으로 수렴한다
- 반복 작업은 복잡도가 커질수록 CronJob → Airflow(배치), Kafka → Temporal(워크플로우)처럼 상태 관리가 내장된 도구로 옮겨간다

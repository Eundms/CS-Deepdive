# AI 네이티브 백엔드 개발

> 서버 개발 조직이 AI를 어디까지, 어떻게 업무/개발 프로세스에 녹일 수 있는지 정리

## 1. 업무/분석 자동화

- **업무 자동화**: 자동 전화, 상품 검수 같은 반복 운영 업무와, 모든 상품의 카테고리 분류처럼 규칙 기반으로는 커버 범위가 제한적이던 작업을 AI로 확장
- **분석 자동화**: async profiler 결과(flame graph)나 heap dump처럼 사람이 직접 들여다봐야 했던 산출물을 AI가 1차로 해석해 "어디를 봐야 하는지"를 먼저 짚어줌

## 2. 개발·운영 도구화

| 도구 | 역할 |
|------|------|
| admin builder | 관리자 화면을 코드 작성 없이 혹은 최소 코드로 자동 생성 |
| admin assist | 어드민 운영 중 반복 문의/조치를 AI가 보조 |
| zero ops agent | 운영 이슈를 사람 개입 없이(또는 최소 개입으로) 진단·조치 |
| code review agent | PR에 대해 1차 리뷰(컨벤션, 잠재 버그)를 자동 수행 |
| doc center | 분산된 기술 문서를 모아 검색/질의응답 가능한 지식 허브로 구성 |

## 3. 공통 실행 환경 먼저

개별 도구를 만들기 전에 **Centralized harness**(여러 AI 에이전트를 조직 차원에서 일관되게 실행), **MCP servers**(AI가 사내 시스템에 표준화된 방식으로 접근), **CLI**(터미널에서 바로 에이전트를 호출)처럼 공통 실행 환경을 먼저 표준화하는 것이 중요하다.

## 4. 조직의 병목 해소: AI-native development

서버 개발 조직의 고질적 병목인 **코드 리뷰 대기 시간**을 AI로 어떻게 줄일지가 핵심 질문이다. 리뷰어 수를 늘리는 대신, AI가 1차 필터 역할을 하거나 리뷰 품질 기준을 상향 표준화하는 방향으로 접근한다.

## 5. 비용과 품질의 균형

더 저렴한(작은) 모델로 교체했을 때 결과 품질이 그대로 유지되는지가 핵심 과제다. 비용-품질 트레이드오프를 정량적으로 평가(eval)할 수 있는 체계가 없으면, 모델을 바꿀 때마다 품질 저하를 감으로 판단하게 된다.

## 핵심 정리

- AI는 단순 반복 업무 자동화를 넘어 운영 진단(zero ops agent)과 개발 프로세스(code review agent, doc center)까지 파고들고 있다
- 이를 지속 가능하게 하려면 개별 도구보다 공통 실행 환경(harness, MCP, CLI)을 먼저 표준화해야 한다
- 모델 교체/비용 절감은 품질을 정량적으로 평가할 수 있는 체계가 전제돼야 안전하게 할 수 있다
